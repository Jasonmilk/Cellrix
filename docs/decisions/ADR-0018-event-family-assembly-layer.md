# ADR-0018: 事件族装配层——经历与证轨成为同一事件流的两个 target

- **状态**: Accepted（2026-09-15 用户拍板：采纳诊断、驳回处方，四案按此冻结）
- **日期**: 2026-09-14（2026-09-15 修订：补 `__ASSEMBLY__` 占位符 / 合并语义 / schema 版本 / 水位线 / 变更驱动）
- **关联**: `Cellrix:ADR-0015`（D8 资产化拼装 / D14 会话域拆分）、`Cellrix:ADR-0016`（证轨资产解耦，五资产边界）、
  `Cellrix:ADR-0017`（资产语言）、`anaphase:ADR-0026`（会话事件流）、`docs/DNA.md` 原则 2/4/5/6/7/8 与铁律 2
- **取代**: 无（在**取数层**补 `Cellrix:ADR-0016` 未覆盖的一面；ADR-0016 的五资产边界不变）

> **跨仓引用一律仓名限定**：`Cellrix:ADR-0016` ≠ `anaphase:ADR-0016`；`ADR-0017` 同理。
> 本 ADR 是**跨仓 ADR 伪装成单仓**：事件族形状来自 `anaphase:ADR-0026`，架构是 `Cellrix ←CAP→ Anaphase`。
> 它的产出（统一经历流）是 prompt 编排的原料，**地位高于「展示层重构」**。

## 1. 背景与问题

现状：`web/assets/base.html` 提供占位符，`web/src/main.rs` 用 `include_str!` + `.replace()`
**平铺拼装**，无构建步骤、**编译期**烧入。四个视图（cockpit / prove-track / chat / flows）
各自拼装，证轨五资产经 `window.CxProveTrack` 桥接，加载序 data → view → ctrl → `__SCRIPT__` 是硬约束。

**问题不在分层，在取数。** 同一批事实被多处重复推导：

| 事实 | 谁在推导 |
|---|---|
| period 列表 | 证轨 `prove_track.data.js`（`/api/sessions` → `periods`）／ 侧栏经历（`script.html` 的 `selectPeriod` 驱动 `#s-side`） |
| 轮次 / 模型名 / 状态 / 时长 | 证轨视图层／经历列表／对话视图各自算 |
| 同一批事件 | 历史路径读 `periods` 事件流；实时路径走 SSE（`chat.js`）——**两套代码** |

⇒ 后果有二：
1. **同一事实多份来源**（与 ADR-0039 / ADR-0040 同一个病根）；
2. **实时与回放是两套实现**，无法保证收敛到同一结果——而「可审计、可追溯」恰恰要求它们收敛。

## 2. 决策

### D1｜引入 target-neutral 装配层（一个资产）

新增 `web/assets/assembly.js`（`window.CxAssembly`）。它**只做三件事**：

1. **事件族身份路由**（稳定 id）
2. **有序 replay**
3. **Turn / Step 坐标发布**

不做别的：不渲染、不格式化、不碰 DOM。渲染留在各 target。

**D1.1｜坐标不是装配层的领域知识，是共享纯函数的输出。**

曾有评审建议把「坐标发布」移出装配层（理由：那是证轨的领域知识，塞进中立层就假中立了）。
**不采纳该形式，采纳其精神**：

- 若把坐标归给证轨，则经历要读坐标就得**依赖证轨** → 直接违反 D2「互不导入」。
- 正解：坐标由**具名共享纯函数** `deriveCoordinates(eventWindow)` 派生，装配层只**发布**它的输出。
  ⇒ 装配层仍然中立（它不定义坐标怎么算），两个 target 仍不互相依赖。
- 同理，**共享 fold 原语**：两个 target 各自持有 State（对），但「怎么算」必须是
  **同一个纯函数**（否则会在更低层复发病根）。共享的是**纯函数与契约**，不是状态与呈现。

### D2｜对话与证轨 = 同一持久事件流的两个 target

- 每个 target 持有**自己的** State 与最终 payload，**互不导入**。
- 两个 target 可以解释同一个 event family，但**不共享最终 display model**——
  共享 display model 会让「改一处、坏两处」，重新耦合。
- 术语对齐：**经历 = Session 坐标；证轨 = Trajectory target。**

### D3｜事件族契约（含合并语义与机器可读 schema）

- 形状：`start` / `update` / `end`，每个事件带**稳定 id**。
- 每个 `(kind, id)` **最多一条 start**。
- 增量必须按 **seq 升序确定性重放**出 State；**不得依赖只存在于实时内存中的状态**。

**合并语义（补齐，原稿缺失）**：

| 规则 | 说明 |
|---|---|
| **seq 由服务端打** | 客户端自增序号永远对不上；seq 的持有者是 `anaphase:ADR-0026` 侧 |
| **幂等 upsert on `(kind, id)`** | 同一窗口 replay 两次必须 deep-equal（验收条 1） |
| **丢弃 `seq ≤ lastSeq`** | 重复投递不得回退状态 |
| **乱序策略** | 显式定义：缓存到缺口补齐，或按 seq 排序后重放 —— 二选一，写死，不两可 |
| **缺口触发显式回拉** | 检测到 seq 缺口 → 回拉补齐，**不把缺口当成「没有事件」** |
| **未知 kind 不静默丢弃** | 显式处理 + 落诊断计数（静默丢弃 = 静默失败） |

**机器可读 schema + 版本字段**：

> 只有散文描述的契约，等于让 `assembly.js` **硬编码形状**，日后必然漂移。

事件族形状必须有一份机器可读 schema（随事件流发布），并带**契约版本号**。
版本号进 `digest()`，让「我按哪一版解释的」成为可查事实。

### D4｜start 未加载 → pending，不构造 State（**有界**）

宁可 pending，不猜。（DNA 原则 7 物理事实优先）

**pending 必须有界**，否则就是一个会无限增长的内存洞：

- 有界：数量上限 + TTL（均来自配置常量，零字面量）；
- 可见：pending 计数暴露给 `digest()`；
- **释放序：多个 pending 必须按 `seq` 排序释放**。按到达顺序释放会破坏确定性
  （到达顺序是**网络事实**，不是**事件事实**）。

### D5｜target 按需激活，append 热路径不重扫

- **读 source 不跑 builder**；首个订阅才做一次完整 replace。
- **append 热路径不得遍历全窗口 / 全 Context / 全 matches / 全已渲染 Node。**
- 累计事实进 State；同 Turn / Step 共享的信息进坐标数据；前序依赖走**索引化读取**。
- **退订即停驱**：原稿只写了「订阅才构建」，缺「没人订阅就停」。无订阅者时不得继续驱动。
- **变更驱动，不是时钟驱动**：发布由**变更**触发，合并窗口显式（microtask flush 或 rAF）。
  「每帧发布一次」把确定性交给了时钟，违反确定性优先（见验收条 5）。
- **订阅者集合不得成为 State 的输入**：惰性只决定「算不算 / 何时算」，绝不决定「算出什么」。

### D6｜零构建依赖不变；但**编译期烧入 ≠ 全量烧入**

仍是 IIFE + `window.Cx*` 命名空间桥；加载序
**`__ASSEMBLY__` → data → view → ctrl → `__SCRIPT__`**（装配层必须排在 data 之前）；
`include_str!` 编译期烧入不变。**不引入模块加载器、不引入打包器**（同 `Cellrix:ADR-0016` D7）。

**修正一处把两件事绑死的写法**：原稿把「零构建」与「全量烧入」并列。
实际上**按路由选择性烧入**即可 —— 零构建与按需加载**可以同时成立**。

### D7｜水位线是一等输出

分不清「**确定这里没有事件**」与「**这里还没收到**」，就无法诚实呈现。

```text
watermark = { lastSeq, gaps: [ [a,b], ... ] }
```

水位线与 `digest()` 一起，把「我确定到哪儿了」从一句散文变成可查事实。

### D8｜`digest()` 可观测

```text
digest() = { lastSeq, eventCount, pendingCount, schemaVersion, fingerprint }
```

> 把「收敛」从**测试期断言**变成**生产期可查**。

## 3. 可直接当回归网的验收条（11 条）

1. 完整窗口 replace 后，产生预期的 State / 坐标数据 / target payload / 锚点 seq；
   **同一窗口 replay 两次必须 deep-equal（幂等）**。
2. 只有 update 的尾部窗口保持 **pending**；补齐唯一 start 后，结果与完整 replace **相同**。
3. 初始历史之后继续实时 append，与回放合并后的完整窗口结果**相同**。
4. 补更早分页只增加更早的行；数据未变的既有 keyed node 值**不被替换**。
5. 重复的可见 delta 保持同一个 key；**变更驱动**（非时钟）发布，合并窗口显式，每窗口最多发布一次。
6. keyed renderer 只消费 `node.data` 与受限坐标 hook，**不扫描**事件窗口 / Context / Node 集；
   加测试接缝：被 instrument 的 Context / Node 代理在**全量扫描时抛错**。
7. 创建 target source **不执行** builder 工作；显式选择或首次订阅才做一次完整 replace；
   **退订后停止驱动**。

**新增 4 条**：

| # | 验收条 | 判据 |
|---|---|---|
| **8** | **纯度** | 禁 `Date.now()` / `Math.random()` / DOM 读 / 全局可变状态。同一盘录像放两遍必须一模一样 |
| **9** | **切分不变性** | 对任意切点 k：`replay(前 k) + live(k..n)` == `replay(all)`。**全篇最该有的一条** |
| **10** | **分块不变性** | 1 / 3 / 7 / 全量任意分块喂入，终态一致 |
| **11** | **digest 可观测** | `digest()` 在生产期可查，且第 9 / 10 条的不变性能由它自证 |

第 2、3、7、9、10 条正是「**可审计、可追溯**」的可执行定义——**回放与实时必须收敛到同一结果**。

## 4. 备选方案与拒绝理由

| 备选 | 拒绝理由 |
|---|---|
| **A. 维持现状**（各视图各取数） | 同一事实多份推导；实时与回放两套代码必然分叉 |
| **B. 抽一个共享渲染函数给各视图调用** | 渲染共享 ≠ 事实共享：State 仍在各处重复推导，病根未除 |
| **C. 把对话与证轨合并成一个视图** | 合并视图 = 放弃两种呈现（轨迹 vs 对话）；且完全没解决取数重复 |
| **D. 引入 ES Module / 打包器做真模块化** | 引入构建期依赖，违背零构建依赖（ADR-0016 D7 已拒） |
| **E. 让装配层同时负责渲染** | 装配层会膨胀成"上帝模块"，重新耦合（DNA 原则 2 极致解耦） |

## 5. 放弃了什么

- **放弃了"每个视图自足"的简单性。** 任何视图都要先经装配层，读代码要多跳一层。
- **放弃了实时路径的即时构造。** start 未到就保持 pending，界面可能短暂空白。
  换来的是**不猜**——空白是诚实的，猜出来的行是假的。
- **放弃了把 display model 共享给两个 target 的便利。** payload 会各存一份（内存换解耦）。
- **放弃了"一次改一处生效"的幻觉。** 两个 target 需各自适配同一 event family 的变化——
  这是刻意的：两个 target 的**呈现本来就不同**，强行统一才是耦合。

## 6. 后果

- **正面**：事实单一来源；实时与回放收敛到同一结果；target 可独立演进；
  新增 target 只需写 target 适配，不动取数。
- **负面**：装配层本身要维护；跨 target 的事件族变更需两处适配；首帧可能 pending。
- **不变式（验收条件）**：
  1. 第 3 节 7 条全部成立；
  2. 既有 DOM 断言全部继续通过（`id="eTblVp"` / `id="eLaneInput"` / `id="eInsp"` / `__proveTrackLoad` 等）；
  3. **`__ASSEMBLY__` 占位符存在且计数为 0**，且其展开位置**早于** data 层
     （派生式断言：占位符清单与实际 `base.html` 占位符一一对应，新增占位符必须同步进本清单）；
  4. `__PROVE_TRACK__` / `__CHAT__` 等占位符在输出中计数为 0；
  4. 输出首字节为 `<!DOCTYPE html>`；
  5. `web/assets/` 全部资产 ≤400 行（DNA 铁律 2）。

> **T5 阻塞（2026-09-15 查明，实测）**
>
> `anaphase` 的 `/v1/chat` SSE 推的是：`data: {"delta": …, "think": …}`（LLM token 增量）与
> `data: {"done": true, "reply": …, "model": …}`（终局）。**它不含 `type` / `seq` / `time`，
> 即不是事件族** —— 事件族（D3）是后端写盘的**离散事件**（`turn/start`、`assistant/reply` …）。
>
> 把 token 增量塞进事件族属于**层次混淆**：token 是**显示通道**的粒（渐进渲染），
> 事件是**记录通道**的粒（权威、可回放）。而且 D3 明确「seq 的持有者是服务端，
> **客户端自增序号永远对不上**」—— **前端无法自行补 seq**，因此 T5 不能在前端实现。
>
> 只有两条路，**待用户裁决**：
> ① **关闭 T5**：实时流只做显示，权威数据走事件流；**历史回放已由 T4 覆盖**。
> ② **升级为跨仓协议扩展**：`anaphase` 在 SSE 中带上事件形状，
> 需 `anaphase:ADR-0026` 与本文同步修订。

> **没有 runner 的回归网是装饰品**。测试期依赖 node（受管 workspace + `NODE_PATH`）≠ 运行期依赖；
> D6 禁止的是运行期构建依赖，不禁止测试期 runner。
