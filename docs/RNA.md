# Cellrix 加载协议（RNA）

> **版本**：v1.0
> **日期**：2026-08-30
> **所属方法论**：phyt-DNA v1.0
> **性质**：本文件定义 Cellrix 的三层加载协议、AI 协作铁律、大版本更新 SOP。所有 AI 协作者必须遵循本协议。

---

## 一、三层加载协议

### 第一层：活跃档案（新会话必读，按顺序加载）

| 顺序 | 文件 | 职责 | 必读 |
|---|---|---|---|
| 1 | `docs/DNA.md` | 宪法：不可变原则 | ✅ 必读 |
| 2 | `docs/RNA.md` | 导航：本文件 | ✅ 必读 |
| 3 | `docs/PLAN.md` | **导航牌：当前阶段** | ✅ **必读** |
| 4 | `docs/GROWTH.md` | 生长：最近 3 次健康快照 | ✅ 必读 |
| 5 | `docs/DEPRECATE.md` | 临终：正在退役的功能 | ✅ 必读 |

**加载规则**：
- 新会话必须按顺序加载第一层全部 5 个文件
- 不允许跳过 PLAN.md（当前阶段导航牌）
- 不允许在未加载 DNA.md 的情况下修改任何代码

### 第二层：规格分卷（按需加载）

| 文件 | 职责 | 何时加载 |
|---|---|---|
| `docs/SPEC.md` | 完整叙事：知识本体 | 需要理解项目全貌时 |
| `docs/spec/philosophy.md` | 哲学分卷 | 涉及设计哲学决策时 |
| `docs/spec/architecture.md` | 架构分卷 | 涉及架构变更时 |
| `docs/spec/contract.md` | 契约分卷 | 涉及接口/协议变更时 |
| `docs/spec/safety.md` | 安全分卷 | 涉及安全相关变更时 |
| `docs/spec/positioning.md` | 定位分卷 | 涉及生态定位时 |

**加载规则**：
- 按需加载，不预先读取所有分卷
- 修改对应模块时，必须先加载对应分卷

### 第三层：决策与历史（按需加载）

| 文件 | 职责 | 何时加载 |
|---|---|---|
| `docs/decisions/ADR-XXXX-*.md` | 架构决策记录 | 涉及已有决策时 |
| `docs/archive/growth/` | 历史生长记录 | 需要回溯历史时 |
| `docs/archive/deprecated/` | 历史退役记录 | 需要了解已退役功能时 |

**加载规则**：
- 只在需要时加载特定 ADR
- 不预先读取所有历史归档

## 二、AI 协作铁律

### 铁律 1：决策拦截
架构/接口变更时，提示创建 `docs/decisions/ADR-<编号>-<标题>.md`（如 `ADR-0001-rust-rebuild.md`）。
- 编号为 4 位数字，按顺序递增
- 引用时使用 `ADR-<编号>`（如 `ADR-0001`）
- 文件名与引用名必须一致

### 铁律 2：DNA 不可修改
- AI 不得修改 `docs/DNA.md`（宪法）
- AI 不得修改 `docs/VISION.md` 的原子原则（可提议，人类最终决策）
- 修改 DNA 等于修改身份，旧身份的信用不会转移

### 铁律 3：PLAN 不记录已完成
- `docs/PLAN.md` 只含当前阶段 + 下一阶段预览 + 阶段总览
- 阶段完成后，详细内容从 PLAN 移除，摘要写入 GROWTH
- 不允许在 PLAN 中堆积已完成的历史记录

### 铁律 4：测试先行
- 每个功能必须有测试
- 测试不通过不合并
- 提交前必须运行 `cargo test --workspace`

### 铁律 5：文档同步
- 代码变更必须同步更新门面文档（README/VISION/SPEC）
- 新增模块必须在 README 的核心模块表中登记
- 性能数据必须在 README 中展示

### 铁律 6：提交信息规范
- 提交信息格式：`<type>(<phase>-<task>): <描述> (ADR-XXXX §<phase>-<task>)`
- 示例：`feat(P1-T2): 布局引擎 DFS 焦点管理 (ADR-0001 §P1-T2)`
- type: feat/fix/docs/refactor/test/chore

### 铁律 7：防腐化
- 超过 3 个阶段未使用的代码必须退役（DEPRECATE）
- 单个文件不超过 500 行（测试文件除外）
- 单个函数不超过 50 行

### 铁律 8：六大工程原则
所有代码必须遵循：
1. 极致解耦
2. 按需加载
3. 按需驱动
4. 极致复用
5. 物理事实优先
6. 确定性优先

## 三、大版本更新 SOP

### 步骤 1：提案
- 创建 ADR 提案，说明大版本变更的原因和范围
- 人类审查 ADR，确认是否启动大版本更新

### 步骤 2：冻结
- 冻结当前版本的 API 和行为
- 创建版本标签（如 v1.0.0）
- 更新 DEPRECATE.md，标记将在新版本中退役的功能

### 步骤 3：迁移
- 按阶段执行迁移
- 每个阶段完成后更新 GROWTH.md
- 保持向后兼容性（除非明确声明破坏性变更）

### 步骤 4：发布
- 运行全部测试
- 更新 README 和所有门面文档
- 创建新版本标签
- 发布更新日志
