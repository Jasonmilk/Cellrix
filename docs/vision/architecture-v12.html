四层是概念，进程边界是部署

进程拓扑回答的是「代码跑在哪」，不是「这层是什么」⇒ 它是横贯四层的部署轴，不是第五层。把它当成一层，会把部署维度混进概念分层。

元原则领域定义提候选，代码给证据，公理来否决。 三阶段：① 领域定义提出候选词（先说清这个概念是什么、边界在哪）；② 代码提供映射证据——优先取代码里已有的词（event_family ⇒ 事件）；代码里没有 ⇒ 须从代码词汇派生（事件 + 流 ⇒ 事件流）；③ 无论哪条通道，都必须过 A2–A5。未被否决的即为最终答案。 并列原则（不替换本条）：V > 0 在哪，真相就在哪。——本条管谁有命名权，Ω 管判据有没有证据力，两件事，不互相替代。
代码是证据方 + 平局裁决方，不是提议方：代码可能反映旧实现、临时变量名或历史债务，把代码当唯一来源会让架构语言被当前实现锁死；但把提议权全交给领域定义，又会退回凭空取名。
冲突时的执行顺序（三段）：① 公理否决（A2–A5，最高）；② 定义 vs 代码冲突 ⇒ 代码胜（平局裁决方，不阻塞推进）；③ 但必须记入迁移债表——当前代码名 ≠ 目标名，列为待迁项。代码胜 ≠ 问题已解决。
1

命名宪法：Ω 判别力 + A0 + T1 + A2–A5

Ω 是元公理，五条命名规则都是它的实例。它们此前并列 ⇒ 会打架、会循环论证；成树之后不会。
T1 不是 A0 的推论。A0（以发生记账）为真时，T1（可拒绝性二分）仍可为假——完全可以有一个按发生记账、但请求仍可被拒的系统。故 A0 是领域事实，T1 是有作用域的设计约定，两者平级自封，不存在推导关系。

显式层级链（冲突裁决顺序）
LΩ · Ω（元公理）　判据必须能排除一个世界 —— 一切判据的判据
L0 · A0（领域事实）　系统以发生为单位记账 —— 代码可判
L0′ · T1（设计不变量）　可拒绝性 —— 与 A0 平级自封，不是 A0 的推论（L0′ 仅为排序，非派生）
L2 · A2–A5（命名规则）　独立，不可被下层覆盖
L3 · C1–C4（闭环校验）　管图的完整性，不管命名
L4 · 代码　只有提议权，无否决权
冲突时自上而下裁决：Ω 检验 → 公理否决 → 代码平局裁决 → 记入迁移债表。「代码为准」仅在其未被 LΩ–L3 否决时成立——层级链显式化后，不存在循环。
代码作平局裁决方的正当性 = 代码侧判据在该世界对上 V > 0；若代码侧无法区分两个世界，则代码不具裁决资格，交给定义侧。
Ω · 判别力（元公理）—— 一切判据的判据
一条断言是判据 ⟺ 它能排除一个世界。能答「它排除的是哪两个世界」 ⇒ V > 0 ⇒ 判据；答不出 ⇒ 装饰，不许写。
这条把喊了几十轮的「判据必须能红」变成了可判的命题：能红 = 存在一个世界让它红 = V > 0。
度量：V(a; A_good, B_bad) = log₂ [ P(通过 | A) / P(通过 | B) ]
三处必须写明的修正：
① V 带世界对为参数，不是判据的固有属性 ⇒ 同一条判据换一对世界，V 就变。正是这一点让 P0b/P0d 正交可推导（它们排除的是不同的世界对），而非诉诸直觉。
② 本领域中 V 是退化的：确定性测试的 P 只能取 0/1 ⇒ V ∈ {0, +∞, −∞}。它是「能不能区分」的是/否，不是分级度量 ⇒ 不要拿它比较两条判据谁更强。
③ 方向：V > 0 ⟹ 能红；能红 ⇏ V > 0。一个在两个世界里都 50% 飘红的测试能红但 V = 0 ⇒ 在确定性前提下两者重合，V < 0 = 极性反了 ⇒ 用 A_good / B_bad 固定极性，不看 |V|。
五条命名规则全是 Ω 的实例（此前并列、会打架；成树后不会）
T1 可拒绝性　＝ Ω 在时间维度　两个世界：已提交 / 未提交 ⇒ 不可分 ⇒ V = 0
A2 机制≠内容　＝ Ω 在语义维度　两个世界：桶 / 桶里的东西 ⇒ 一词两义，反查不可分
A3a 无同名占用　＝ Ω 在仓库维度　两个世界：同物 / 异物 ⇒ grep 可判
A3b 结构断言　＝ Ω 在理解维度　两个世界：断言真 / 断言假 ⇒ 核对可判
A4 具象性　＝ Ω 在指认维度　两个世界：这段代码 / 那段代码 ⇒ 词太抽象则不可分
A5 一物一名　＝ Ω 在反查维度　两个世界：一个词指两个东西 ⇒ 反查不可分
推论（不再单列 A6）：换同义词不改变两个世界的可分性 ⇒ V = 0 ⇒ 白做。这正是「用同义词解决同义撞车 = 循环论证」的机制解释。
起点
A0 · 领域事实
以发生为单位记账
系统数的是发生，不是「想做」。48 次相同提问 = 48 个身份，因为它们是 48 次发生。
判据：身份是否按发生计数？（代码可判）
地位：领域事实起点。边界：到达次数 ≠ 业务身份——用户提交一次、客户端重试 48 次，物理上到达 48 次；业务上算几次由幂等键 / 请求 ID / 去重边界决定，不由 A0 决定。
推论
T1 · 设计约定（非推论）
可拒绝性
这是设计约定，不是从 A0 推出的定理。原文：尚未提交、可被拒绝或撤销的称意图；已提交、不可改写的记录称事实（事件）。事件可被后续事件更正或补偿，但历史记录本身不被覆盖。
二分，无第三类——但这是有作用域的约定，不是已证明穷尽的分类。
判据：能否被拒绝？（先问：它是变更单元吗？）
Ω 检验：排除的世界对 = 已提交 / 未提交；V > 0 ⇒ 是判据
命中：Intent 日志 → 事件流；挂起意图仍属意图域（见 ②）
判据前置：先看它是不是变更单元——写入是否进入事件流 / 是否必须经 apply() ⇒ 是 ⇒ 受本约定约束；否 ⇒ 不受（声明 / 观测 / 触发源 / 投影）
已归位
A2
机制 ≠ 内容
容器与内容不合成一词。桶是桶，桶里的东西是桶里的东西。只管语义分层，不管词能否指代到代码（那是 A4）。
判据：它是桶，还是桶里的东西？
Ω 检验：排除的世界对 = 容器 / 内容；一词两义 ⇒ 反查不可分 ⇒ V = 0
命中：终端桥（机制）vs 桥进来的外部 TUI（内容）；pane（容器）vs pane 里的进程状态（内容）
可判
A3a · 仓库内
无同名占用
该词在本仓库中是否已指别物？grep 一次即判。已指别物 ⇒ 改名；未指 ⇒ 通过。
判据：grep 出来是不是同一个东西？
Ω 检验：排除的世界对 = 同物 / 异物；grep 命中即 V > 0
命中：视图层（view.js 即只读派生，无冲突）
可陈述
A3b · 跨语境
名字的结构断言为真
每个借来的词都携带一条结构断言。把它写出来，与设计一对一比对：假 ⇒ 改名；真 ⇒ 保留并可借势。断言为真但存在著名同名 ⇒ 保留 + 加限定词。
定性：这是「可审议的语义核对」，不是客观判定器——它依赖选取哪种词义、在哪个语境判断。
判据：把这个词的断言写出来，它对吗？
四字段必须记录：本文采用义 · 来源语境 · 对应架构属性 · 为何其他常见义不适用
Ω 检验：排除的世界对 = 断言真 / 断言假；核对一对即判
命中：WAL 断言「日志守卫另一个 store」⇒ 与设计相反 ⇒ 假 ⇒ 改名；视图层 断言「只读派生、自身不存数据」⇒ 真 ⇒ 借势；壳层 断言「命令行解释器」⇒ 假 ⇒ 改名
A4
具象性（两条要求）
① 代码映射：概念能映射到明确的模块 / 类型 / 接口 / 代码区域——不必是单独一行代码。
② 架构定义：概念的职责边界明确，即使它没有单一代码位置（「契约层」「适配层」「进程轴」等架构概念属此类）。
判据：能指出来是哪段代码，或说清职责边界吗？
Ω 检验：排除的世界对 = 这段代码 / 那段代码；指认不到 ⇒ 不可分 ⇒ V = 0
与 A2 的适用顺序：先 A2（判语义分层：桶 vs 内容），再 A4②（验职责边界是否可陈述）；结论冲突时以 A2 为准——A2 管语义，A4② 只管表达。
命中：外延/边界层 → 适配层；状态树 → 对象图
A5
一物一名
禁第二份清单、禁一词两义。异物不共名，同物不两名。
判据：反查唯一吗？
Ω 检验：排除的世界对 = 一词一物 / 一词两物；反查重复 ⇒ 不可分 ⇒ V = 0
命中：mode 拆为运行模式/交互模式；capability 拆为权限分级/模态；turn/job 段自带序号
A3 为什么要拆两条：单靠 grep 会丢掉跨语境判决
A3a 只能查仓库内部：grep 一次即可判定「该词在本仓库是否已指别物」。但 WAL 在本仓库里根本不存在——grep 一次也命中不了，A3a 抓不到它。 而对 WAL 的否决，实际依据的是跨语境语义（数据库 WAL 守卫另一个 store，与本设计相反）。 ⇒ 仅靠 A3a 无法复现这个判决。同理「视图层」「壳层」的判定也都是跨语境的，grep 判不出来 ⇒ 必须有 A3b。
拆法：A3a 管仓库内（grep 可判）；A3b 管名字携带的结构断言——写出来就能核对。
为什么 A3b 比「陌生人想到什么」强：断言是可陈述、可辩论、有对错的，争执时可查该词的标准定义来裁决；而「想到什么」是纯主观的，无从裁决。把不可判的判断，换成可判的核对。
复核：A3b 能复现全部三个判决 —— WAL（断言假·改名）· 视图层（断言真·借势）· 壳层（断言假·改名）。
⚠️「A0 ⇒ T1」这条推导不成立。
「以发生为单位记账」不蕴含「可拒绝性二分」。反例：① 一个系统按发生记录每个到达的请求，但请求仍可能被拒绝 ⇒ 满足 A0 而不满足 T1；② 不可修改的事实事件，之后仍可用更正 / 撤销 / 补偿事件改变其业务效力 ⇒ A0 为真而 T1 的「不可撤销」边界并不自动成立。
改法：T1 明确标为设计约定 / 设计不变量，与 A0 平级自封，不再声称被推出。这是清楚的工程语义，但不需要伪造成逻辑推导——伪造推导比承认约定更危险，因为它会让下游把约定当定理使用。
T1 作用域：变更单元判据 + 应用示例
判据（不是名单）：变更单元 ⇔ 该对象的写入是否进入事件流 / 是否必须经 apply()。
⇒ 是 ⇒ 受 T1 约束；否 ⇒ 不受（声明 / 观测 / 触发源 / 投影）。来一个新对象用判据判定，不必再枚举一次 ⇒ 下表是判据的应用示例，不是边界定义。
对象是否变更单元归属
已提交的状态变更事件是事实（不可撤销，可补偿）
未提交的意图 / 挂起意图是意图（可拒绝）
配置声明（运行模式等）否契约层声明语义，不是状态
外部观测（PTY 存活检查等）否观测事件（记录观察结果，非变更）
定时任务触发否触发源；其产生的结果才是变更单元
校验失败否拒绝本身是事实（拒绝了什么），不是变更
投影缓存（对象图、视图、渲染缓存）否派生投影，可重建，不受 T1 约束
已提交但副作用未完成的操作作用域边界事件已记 / 效果未做的窗口 ⇒ 需 Transactional Outbox 或等价机制（见 P1 前数据契约）
这张表是判据的应用示例，也是「二分」的作用域声明。T1 对它未覆盖的对象不作主张——因此它不是已证明穷尽的分类，而是有作用域的约定。
⚠️ 表中「作用域边界」不是第三类。它表示T1 对该行不作主张（作用域之外）；而「第三类」表示T1 主张存在第三类事物。两者形式相似、性质相反——混读会把「不作主张」误读成「主张存在第三类」。
公理完备性的验证方式要换
「120 种优先级排列结论一致」只能证明规则之间无环——一条零命中的规则放在任何位置都不会改变结论，所以那个一致性是空洞的。真正的无环验证是：任一条规则的判据不引用另一条规则。
⇒ 改用可复核的两条：
① 无环：任一条规则的判据不引用另一条规则（读一遍即可验，不需要 120 次排列）。
② 完备：收集 10 个已知有歧义的术语，看 A2–A5 能否全部捕获。
完备性的作用域必须限定：「事件广播无家」「计数错误」扫不出来，因为它们不是命名问题——前者是图的结构缺口，后者是算术。 用它们判定「命名公理不完备」是范畴错误。
⇒ 不新增 A6/A7（那会模糊公理与不变量的边界），而是把闭环校验独立成 C 组：命名规则管「叫什么」，闭环规则管「图全不全」。
C1 反查唯一 · C2 无概念占两层（同维度内；跨维度双标除外）· C3 无概念无家 · C4 计数自洽（T0 前只验弱自洽）

意图与事实的分界

本约定划出全图最重要的一条界（注意：是约定，不是从 A0 推出的定理）。所有改名都由它开始。挂起意图不是第三态——它能被拒绝，按本约定归为意图。

代码证据（仓库全站在「事件」这一边）： EventType::Purge · event_family.js · period/purge · turn/start · ref/move ——全是 Event，没有一个是 Intent。 ⇒ 「Intent 日志」这个词把 A1 那条线抹掉了，所以它不是「名字不好听」，是定义错了。
关于意图的事实：事件流里完全可以有 IntentProposed / IntentRejected 记录—— 它们是「关于意图的事实」，不是意图本身。这句同时也是挂起意图不破坏 T1 二分的根据：意图留在队列里（可拒绝），只有关于它的事实进入事件流。
挂起意图不是第三态：T1 的二分不破
若把 pending 称为「第三态（既非意图也非事实）」，在形式上违反排中律——T1 声称意图/事实穷尽一切，pending 声称两者都不是，二者不能同真。
按 T1 自己的判据判定：pending 能被拒绝（这正是确认门的意义）⇒ 它就是意图。 它不是第三类事物，是队列里的一条意图；其持久化形态是 IntentProposed 等关于意图的事实。T1 二分保持完整，无需增补第三类。
推论：挂起队列是派生状态，由事件流重放重建，不需要单独持久化机制。
⇒ 唯一剩下的决策是：重放后，指向已失效目标的意图（如「向某个已消失的 pane 注入按键」）该如何处理？
(a) 原样呈现　(b) 丢弃　(c) 标记 stale、降级为「需重新确认」
→ 我倾向 (c)：不丢也不自动生效，且因队列由重放派生，与 P0d 单一写入者判据不冲突。

#10 WAL：元原则根本不保护它
本系统的事件溯源链是 追加 → 重放 → 对象图 → 视图，即 log 本身即是 store（事件源）。

裁定：WAL 双违规 —— A3b（结构断言「日志守卫另一个 store」为假）+ A4（映射不到任何代码词汇） ⇒ 改名「事件流」。

A3b 四字段样例（全表唯一已记录实例，其余待补）：采用义「事件的有序序列」· 来源语境「event_family / EventType::Purge」· 对应架构属性「追加 · max+1 · 尾换行」· 为何其他义不适用：数据库 WAL 守卫另一个 store，此处 log 就是 store。
