## 1. 现状：量到的（不是印象）

| 事实 | 出处 / 实测 |
|---|---|
| 页面**整体滚动**（没有 app-shell 高度链） | 视图容器 `#view-*` 无确定高度 ⇒ 子元素无法 `flex:1` 填满 |
| 对话两栏 `240px + 1fr` | `components.html` `.chat-grid` |
| 两个面板的**窗口**上限是 `--pane-h: min(70vh,720px)` | 本轮临时收敛（原为 `420px` / `480px` 两个常数，各自裁掉 581px / 6254px 内容） |
| 证轨：侧栏 `240px` + 主区；三轨条高 `24px`，标签列固定 `58px` | `prove_track.css` |
| 检查器：`min(430px,100vw)` `position:fixed`；**<1180px 转模态** | `prove_track.css`，`all_views_test.js` 断言 `aria-modal` |
| 实测视口 | 1440×813（Chrome headless，本轮所有几何数字都在此取得） |

**一句话**：现在没有"几何契约"，只有**各处各自的常数**。用户原话「布局比较差」；
本轮的根因修复只保证了**盒子按内容长**，**没决定谁填满、谁滚动**。

## 2. 必须一次回答的五个问题

### Q1 几栏？
- 现状：对话 = 2 栏（经历列表 + 消息流）；证轨 = 2 栏（经历列表 + 轨迹）+ 抽屉式检查器。
- **建议：保持 2 栏，但把"检查器"从"覆盖层"改为"第三栏"。**
  理由：检查器现在 `position:fixed` 浮在内容上——本轮已修过「动作层压在正文上」，
  同一形状不应留在主布局里；**覆盖式抽屉是"内容被压"的温床**。
  代价：≥1180px 时主区变窄；<1180px 仍退化回模态。

### Q2 比例？
- 现状：`240px + 1fr`（侧栏固定，主区吃剩余）。
- **建议：经历列表给一个下限与一个上限（如 `clamp(200px, 18vw, 320px)`），不用纯固定值。**
  理由：固定 240px 与内容无关；18vw 是"设备给的比例"，不是常数。
  **待裁决点**：是否接受 `vw` 派生（若否，则用固定 + 断点表，代价是要维护两处）。

### Q3 谁滚动？（**本契约的核心**）
- **建议：每个面板有且只有一个滚动上下文，且它是"填满可用高度"的那一个容器。**
  具体：`.chat-msgs` 与 `.ses-side`（证轨侧栏同理）**只能有一个** `overflow-y:auto`，
  其高度由布局给出（`flex:1 1 auto; min-height:0`），**不再设 `max-height` 常数**。
  理由：本轮三次缺陷（行被压、卡片溢出、`)--pane-h` 常数）全是"多个固定高度叠加"的产物；
  `min-height:0` 是 flex 子项能真正滚动的必要条件。
  代价：需要**一条到视口的高度链**（见 Q4）。

### Q4 谁固定？
- 现状：没有任何东西固定——整页滚。
- **建议：外壳固定高度（`html,body{height:100%}`），`#view-*` 填满，面板内部各自滚；
  只有"消息流/轨迹"这一处滚到底。** 输入框、工具条、统计栏**不滚**（它们在列内固定）。
  理由：「输入框漂到页面下方」与「统计栏随内容滚走」都是可复现的抱怨来源。
  **待裁决点**：是否接受外壳吃满视口（`height:100%` + `overflow:hidden` on body）。
  这会改变**全部四个视图**（cockpit/flows/prove-track/chat）的滚动行为 ⇒ 是本契约里影响面最大的一条。

### Q5 窄屏怎么退化？
- **建议：≥1180px 三栏并排（Q1）／760–1180px 侧栏可收起、检查器模态／<760px 单列，
  经历列表改为抽屉。** 折点沿用现有的 1180（已有 `narrowMQ`），只新增 760 一个。
  理由：现有代码只有 1180 一个折点；折点越少越不容易互相打架。

## 3. 判据（什么算"契约已满足"）

1. **`layout_test.js` 全绿**，并**新增**三条：① 面板任一滚动容器的 `scrollHeight` 不因
   另一个容器的存在而改变；② 输入框在消息区最长时仍可见（在视口内）；
   ③ ≥1180px 时检查器**不与主区重叠**（`elementFromPoint` 判据，与「动作层不得压正文」同一把尺）。
2. **没有 `max-height` 常数**：`--pane-h` 之类由视口派生的值允许；
   `420px`/`480px` 这类与内容无关的常数**不允许**（grep 判据，扫描 `.chat-msgs`/`.ses-side`/轨迹容器）。
3. **`verify_live.py` 59 项不降**，`dom_contract.md` 重新生成后与源码一致。

## 4. 本契约**不**决定

- 视觉（配色、圆角、阴影、令牌）——归 ADR-0015 / 017。
- 三轨条的高度与对齐（`24px`）——本轮已列为独立问题，**不属于"谁填满/谁滚动"**。
- 检查器内部的分区与字段——归证轨自己的契约。

## 5. 为什么必须"先契约、后动手"

高度链与列划分是**同一个决策的两个面**：Q1（几栏）决定 Q3（谁滚）与 Q4（谁固定）。
先做高度链、后改栏数 ⇒ **高度链要重算**（谁填满、谁滚动、谁固定全变）。
这与本项目已确立的「两个半步若共享一个决策，必须一次做完」是同一形状；
2026-09-16 已因此返工过一次（`3b-3` 与 `4b` 合并且返工）。
